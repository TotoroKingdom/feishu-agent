## 1. 项目概述

### 1.1 项目背景

企业项目周报通常依赖员工手工整理飞书项目数据、GitHub Issue、Pull Request、Commit、里程碑和风险事项。该过程重复、耗时，且容易出现数据遗漏、统计口径不一致、结论缺少证据等问题。

本项目建设一个独立部署的飞书 Agent。系统每周自动创建周报生成任务，在飞书中请求员工确认。员工确认后，Agent 从飞书多维表格和多个 GitHub 仓库读取项目数据，进行数据校验、异常诊断、自动重试、证据整理和周报生成。最终发布前再次进入 Human-in-the-loop 审批；审批通过后，Agent 自动创建飞书文档、向指定飞书群发送摘要，并将本次执行结果归档到飞书多维表格。

该项目的主要目标不是替代完整项目管理系统，而是作为求职作品，完整展示生产级 AI Agent 的规划、Tool Calling、Agent Loop、LangGraph 状态编排、Human-in-the-loop、状态恢复、可追溯生成、安全边界和可观测能力。

### 1.2 核心目标

1. 展示基于 LangGraph 的长流程 Agent 编排能力。
2. 展示 Agent 在多数据源、多工具和异常场景下的自主诊断循环。
3. 展示 Human-in-the-loop 暂停、人工补充、审批和恢复执行。
4. 展示飞书机器人、交互卡片、多维表格、云文档和群消息的完整集成。
5. 展示 GitHub 多仓库研发数据采集、融合、统计和证据引用。
6. 展示写操作审批、执行计划冻结、幂等控制、审计和敏感信息保护。
7. 通过独立 Web 管理后台展示 Agent 执行轨迹、节点状态和 Tool 调用详情。

### 1.3 核心用户

- 企业内部员工：周报发起人、确认人和最终发布人。
- 项目管理员：首次配置项目、仓库、飞书资源、定时规则和提示词。
- 开发者或面试官：通过 Web 后台观察 Agent 的执行链路和工程设计。

## 2. 产品范围

### 2.1 MVP 范围

MVP 仅支持一个项目，但一个项目可以绑定多个 GitHub 仓库，例如前端仓库、后端仓库和部署仓库。

MVP 必须支持：

- 企业自建飞书应用与机器人。
- 单项目、多 GitHub 仓库。
- GitHub Fine-grained Personal Access Token 鉴权。
- 飞书多维表格作为项目管理主数据源。
- GitHub 作为研发活动数据源。
- 每周定时创建待确认周报任务。
- 飞书机器人私聊交互卡片。
- 两阶段 Human-in-the-loop。
- 数据完整性校验和异常诊断循环。
- 项目周报自由生成，但输出必须有结构化中间结果。
- 关键结论证据绑定、统计时间范围和置信度。
- 发布为飞书文档、群消息摘要和多维表格归档记录。
- 独立 Next.js Web 管理后台。
- PostgreSQL 持久化、Redis 缓存与运行控制。
- OpenAI 兼容 LLM Provider，默认 DeepSeek。
- Docker 化部署。

### 2.2 明确不做

MVP 不实现以下功能：

- 多企业、多租户和飞书应用商店上架。
- 多项目并行管理。
- GitHub App、GitHub OAuth。
- Jira、禅道、GitLab、Gitee 等其他平台。
- 完整项目管理系统和复杂 RBAC。
- 无人工确认的自动发布。
- Agent 自动修改 GitHub Issue、PR 或代码。
- 向量数据库、企业知识库和通用 RAG。
- 自由访问任意外部 URL。
- 移动端独立应用。
- 复杂 BI 图表平台。

## 3. 核心业务流程

### 3.1 主流程

1. 定时调度器根据项目配置，在每周指定时间创建周报运行实例。
2. Agent 加载项目配置、统计时间范围、绑定仓库和飞书资源。
3. Agent 生成“执行范围草案”，包括时间范围、仓库列表、数据源、报告目标和预计发布位置。
4. 飞书机器人向员工私聊发送确认卡片。
5. 员工可以：
   - 确认开始生成；
   - 修改统计时间范围；
   - 修改仓库范围；
   - 补充生成要求；
   - 取消本次运行。
6. LangGraph 在第一审批节点暂停，并持久化 Checkpoint。
7. 员工确认后，Agent 恢复运行，读取飞书多维表格和 GitHub 数据。
8. Agent 对数据执行标准化、字段映射、去重、时间过滤和完整性校验。
9. 如发现数据缺失、冲突或 Tool 调用失败，进入诊断循环。
10. 数据满足生成条件后，Agent计算项目指标、构建证据集合并生成周报。
11. Agent 对周报执行事实核验，确保关键结论与证据一致。
12. Agent 生成发布预览和冻结后的执行计划。
13. 飞书机器人向员工发送最终发布确认卡片。
14. 员工可以：
    - 确认发布；
    - 修改补充说明；
    - 要求重新生成；
    - 取消发布。
15. LangGraph 在第二审批节点暂停。
16. 员工确认后，Agent依次：
    - 创建飞书周报文档；
    - 向指定群发送摘要和文档链接；
    - 向飞书多维表格写入执行归档记录。
17. Agent 校验所有写操作结果，更新运行状态并通知员工。
18. Web 后台展示完整执行轨迹、节点耗时、Tool 调用、审批记录和最终产物。

### 3.2 两阶段 HITL

#### 第一阶段：生成确认

目的：确认本次运行范围，不产生业务写入副作用。

确认内容：

- 项目名称；
- 统计开始与结束时间；
- GitHub 仓库列表；
- 飞书多维表格；
- 周报生成要求；
- 预计发布群；
- 数据读取计划。

第一阶段确认后，Agent 才能正式读取和分析数据。

#### 第二阶段：发布确认

目的：确认最终报告内容和所有外部写操作。

确认内容：

- 周报摘要；
- 关键指标；
- 主要风险；
- 证据完整性状态；
- 将创建的飞书文档；
- 将发送消息的群；
- 将写入的多维表格；
- 冻结后的执行计划；
- 执行计划哈希值。

员工确认“发布周报”后，Agent可以连续完成已审批计划内的写操作。若目标资源、发布内容类型、写入步骤或接收对象发生变化，必须重新进入第二阶段审批。

## 4. Agent Loop 设计要求

### 4.1 诊断循环

Agent 遇到以下情况时，不得立即失败：

- GitHub API 请求超时或限流；
- 某个仓库不可访问；
- 飞书多维表格字段缺失；
- 数据时间范围不一致；
- Issue、PR 或任务记录重复；
- 项目成员无法匹配；
- 里程碑数据与 GitHub 活动冲突；
- LLM 输出缺少必要结构；
- 关键结论没有证据；
- 发布操作部分成功、部分失败。

诊断循环必须遵循：

1. Observe：记录错误、缺失字段和当前状态。
2. Diagnose：判断问题类型、影响范围和可恢复性。
3. Plan：生成下一步修复动作。
4. Act：调整参数、重新调用 Tool、使用降级数据或重建中间结果。
5. Verify：重新执行校验。
6. Continue or Escalate：校验通过则继续；达到上限则请求人工补充。

### 4.2 自动恢复策略

- 单个 Tool 默认最多重试 3 次。
- 重试采用指数退避。
- GitHub 单仓库失败时，其他仓库仍应继续采集。
- 非关键字段缺失可以降级生成，但必须在报告中标记。
- 关键数据缺失时必须暂停，不得伪造。
- 进入人工补充前，Agent必须说明：
  - 缺失了什么；
  - 已经尝试了什么；
  - 为什么无法自动解决；
  - 员工需要提供什么；
  - 补充后会从哪个节点恢复。

### 4.3 人工补充恢复

员工通过飞书卡片补充信息后，系统必须从已有 Checkpoint 恢复，不得重新执行所有已成功步骤。恢复前应重新校验补充内容。

## 5. 周报内容要求

### 5.1 周报类型

MVP 生成项目周报，重点包括：

- 本周项目概览；
- 任务完成率；
- 已完成事项；
- 延期任务；
- Issue 变化；
- Pull Request 状态；
- Commit 与仓库活跃情况；
- 里程碑进度；
- 人员负载；
- 风险事项；
- 下周计划；
- 需要关注或决策的事项。

### 5.2 自由生成与结构化中间结果

最终周报允许由 Agent 根据用户提示词自由组织章节和表达，不强制固定模板。

但是在生成最终自然语言前，必须生成并校验结构化中间结果，至少包含：

```json
{
  "summary": "",
  "progress": [],
  "metrics": {},
  "delayed_items": [],
  "risks": [],
  "workload": [],
  "next_actions": [],
  "decisions_needed": [],
  "evidence": [],
  "confidence": 0.0,
  "data_quality": {
    "status": "complete|partial|blocked",
    "missing_items": [],
    "warnings": []
  }
}
```

最终报告不得直接基于未经校验的原始上下文自由生成。

### 5.3 可追溯性要求

每项关键结论必须包含：

- 结论内容；
- 数据来源类型；
- 来源资源 ID；
- 可点击链接；
- 统计时间范围；
- 证据摘要；
- 置信度；
- 是否为事实、推测或待人工确认。

证据来源包括：

- GitHub Issue；
- GitHub Pull Request；
- GitHub Commit；
- GitHub 仓库统计；
- 飞书多维表格项目记录；
- 飞书多维表格任务记录；
- 飞书多维表格风险与计划记录。

无法被数据支持的内容必须明确标记为“推测”或“待人工确认”，不得以确定事实表达。

### 5.4 指标口径

MVP 至少计算：

- 本周新增 Issue 数；
- 本周关闭 Issue 数；
- 当前未关闭 Issue 数；
- 逾期 Issue 或任务数；
- 本周新增 PR 数；
- 本周合并 PR 数；
- 长时间未审查 PR 数；
- 本周 Commit 数；
- 活跃贡献者数；
- 里程碑完成率；
- 计划任务完成率；
- 每位成员的任务与代码活动负载。

所有指标必须在代码层完成确定性计算，LLM 只负责解释，不负责直接计算。

## 6. 飞书功能需求

### 6.1 企业自建应用

系统采用企业自建飞书应用，并启用机器人能力。应用必须支持：

- 接收机器人私聊消息；
- 接收交互卡片回调；
- 发送私聊消息；
- 向指定群发送消息；
- 读取和写入指定多维表格；
- 创建飞书文档；
- 获取必要的用户与群基础信息。

所有回调必须完成合法性验证、幂等校验和快速响应。

### 6.2 首次配置向导

管理员首次与机器人交互时，Agent通过对话和卡片逐步收集：

- 项目名称；
- 项目描述；
- GitHub PAT；
- 一个或多个 GitHub 仓库；
- 飞书多维表格标识；
- 多维表格字段映射；
- 发布群；
- 周报接收人；
- 每周执行时间；
- 项目时区；
- 默认统计区间；
- 默认生成提示词。

每一步配置都必须即时校验：

- PAT 是否有效；
- 仓库是否存在且有读取权限；
- 多维表格是否可访问；
- 字段是否完整；
- 发布群是否可发送消息；
- 文档创建能力是否可用；
- 定时规则是否合法。

配置完成后生成确认摘要，管理员确认后持久化。

### 6.3 交互卡片

至少实现以下卡片：

1. 首次配置卡片；
2. 生成范围确认卡片；
3. 数据缺失补充卡片；
4. 周报生成进度卡片；
5. 发布预览与确认卡片；
6. 执行成功卡片；
7. 部分失败与补偿操作卡片；
8. 运行取消卡片。

卡片按钮必须防止重复点击。相同回调重复到达时不得重复执行。

## 7. GitHub 集成需求

### 7.1 鉴权

MVP 使用管理员提供的 Fine-grained Personal Access Token。

要求：

- Token 只允许在创建和更新时提交；
- Token 必须加密后保存；
- API 查询和后台页面不得返回明文；
- 日志、异常、Trace、LangGraph State 和 Prompt 中不得出现明文；
- 必须支持 Token 更新和失效检测；
- Token 权限不足时提供明确提示。

### 7.2 数据采集

每个项目可绑定多个 GitHub 仓库。

至少读取：

- Repository 基础信息；
- Issues；
- Pull Requests；
- Commits；
- Reviews 或审查状态；
- Milestones；
- Contributors；
- Actions 运行摘要，可作为可选功能。

数据采集必须支持分页、限流识别、超时、重试和增量时间过滤。

### 7.3 数据标准化

不同仓库的数据必须映射到统一内部模型，并保留：

- 原始 ID；
- 仓库 ID；
- URL；
- 创建时间；
- 更新时间；
- 状态；
- 作者；
- 负责人；
- 标签；
- 里程碑；
- 原始数据摘要；
- 抓取时间。

## 9. LangGraph 工作流要求

### 9.1 建议节点

工作流至少包含以下节点，Codex 可以在技术设计阶段拆分或合并，但不得丢失对应职责：

1. `load_project_config`
2. `build_generation_scope`
3. `request_generation_confirmation`
4. `wait_generation_confirmation`
5. `collect_feishu_data`
6. `collect_github_data`
7. `normalize_data`
8. `validate_data`
9. `diagnose_problem`
10. `repair_or_retry`
11. `request_human_input`
12. `calculate_metrics`
13. `build_evidence`
14. `generate_structured_report`
15. `verify_grounding`
16. `render_report`
17. `build_publish_plan`
18. `request_publish_confirmation`
19. `wait_publish_confirmation`
20. `create_feishu_document`
21. `send_group_summary`
22. `archive_report_record`
23. `verify_side_effects`
24. `compensate_partial_failure`
25. `complete_run`
26. `cancel_run`
27. `fail_run`

### 9.2 状态要求

LangGraph State 只保存运行所需的业务状态和安全引用，不保存明文密钥。

至少包含：

- run_id；
- project_id；
- requester_id；
- current_stage；
- report_period；
- selected_repositories；
- user_instructions；
- collected_data_refs；
- validation_result；
- retry_counters；
- diagnosis_history；
- structured_report；
- evidence_refs；
- publish_plan；
- publish_plan_hash；
- approval_status；
- artifact_refs；
- error_summary；
- timestamps。

大型原始数据不得直接全部写入 Checkpoint，应存入 PostgreSQL 或对象存储后保存引用。

### 9.3 Checkpoint 与恢复

- 所有 HITL 节点前必须写入 Checkpoint。
- Tool 执行成功后必须记录可恢复状态。
- 服务重启后可以恢复等待审批和执行中的任务。
- 重复恢复不得重复产生外部副作用。
- 每次恢复必须验证审批人、运行状态和计划哈希。

## 10. 外部副作用与安全边界

### 10.1 可自动执行的读取操作

以下操作可以在第一阶段确认后自动执行：

- 读取 GitHub 仓库数据；
- 读取飞书多维表格；
- 计算指标；
- 生成中间结果；
- 生成报告预览；
- 执行事实核验。

### 10.2 必须审批的写操作

以下操作必须在第二阶段确认后执行：

- 创建飞书文档；
- 向飞书群发送消息；
- 向多维表格写入周报归档；
- 修改项目配置；
- 修改定时规则；
- 变更发布目标；
- 重新执行正式发布。

### 10.3 执行计划冻结

发布确认前必须生成结构化执行计划，至少包含：

```json
{
  "run_id": "",
  "document_target": {},
  "group_message_target": {},
  "archive_target": {},
  "content_version": "",
  "operations": [],
  "plan_hash": ""
}
```

审批后实际执行内容必须与计划哈希一致。发生以下变化时必须重新审批：

- 目标群变化；
- 多维表格变化；
- 文档内容版本变化；
- 新增写操作；
- 删除原审批操作；
- 接收对象变化；
- 报告统计时间范围变化。

## 16. 安全要求

### 16.1 密钥安全

- GitHub PAT、飞书密钥和 LLM API Key 不得明文入库；
- 使用独立 `APP_ENCRYPTION_KEY` 加密业务凭证；
- 环境密钥不得通过后台接口返回；
- 日志必须进行敏感字段过滤；
- Trace 和 Agent State 不得包含明文 Token。

### 16.2 飞书回调安全

- 验证飞书回调来源；
- 防止重放；
- 对回调事件 ID 做幂等记录；
- 回调接口快速响应，耗时任务异步进入执行队列；
- 只允许配置的用户进行管理员操作。

### 16.3 Prompt Injection 防护

GitHub Issue、PR、Commit 和多维表格文本均视为不可信外部数据。

要求：

- 外部文本只能作为数据，不得作为系统指令；
- Tool 白名单由代码控制；
- LLM 无权动态创建新 Tool；
- 所有写操作依赖结构化执行计划和人工审批；
- 报告引用外部内容时进行长度限制和必要清洗。

### 16.4 审计

所有管理员配置变更、人工审批、外部写操作、失败补偿和凭证更新必须记录审计日志。

## 17. 可靠性要求

### 17.1 幂等

以下操作必须幂等：

- 定时任务创建；
- 飞书事件处理；
- 卡片按钮回调；
- LangGraph 恢复；
- 飞书文档创建；
- 群消息发布；
- 多维表格归档；
- 失败重试。

建议为每个副作用操作生成唯一 `idempotency_key`。

### 17.2 部分失败

发布阶段可能出现：

- 文档创建成功，群消息失败；
- 文档和群消息成功，归档失败；
- 请求超时但实际操作已成功。

系统必须先查询实际结果，再决定重试。不得盲目重复创建文档或重复发送群消息。

### 17.3 取消

员工在正式发布前可以取消运行。已经进入副作用执行阶段后，取消只能阻止尚未执行的操作，已完成操作必须记录，不得伪造回滚成功。

### 17.4 并发控制

同一项目、同一报告周期只允许一个活动运行。重复触发应复用现有运行或返回明确提示。

## 18. 性能要求

在单项目、最多 5 个 GitHub 仓库的 MVP 规模下：

- 飞书回调接口应在 3 秒内完成响应；
- 后台普通查询接口 P95 小于 800ms；
- 单次周报生成在外部 API 正常时目标不超过 2 分钟；
- 人工等待时间不计入运行耗时；
- 单个 Tool 调用必须有独立超时；
- 大批量 GitHub 数据必须分页和限制最大采集量；
- 原始数据应复用缓存，避免重新生成时重复拉取全部数据。

## 21. 验收标准

MVP 只有同时满足以下条件才算完成：

1. 管理员可以通过飞书完成首次项目配置。
2. 一个项目可以绑定至少两个 GitHub 仓库。
3. 系统可以按周创建周报任务并发送第一阶段确认卡片。
4. 员工可以修改范围、补充提示、确认或取消。
5. Agent 能读取飞书多维表格和 GitHub 数据。
6. 指标由确定性代码计算，而不是由 LLM 猜测。
7. Agent 能发现数据缺失并进入诊断循环。
8. 自动修复失败后，可以向员工提出具体补充请求。
9. 员工补充后可以从 Checkpoint 恢复。
10. 最终周报具有结构化中间结果。
11. 每项关键结论可以追溯到具体证据。
12. 无证据内容会被标记或阻止作为事实发布。
13. 发布前可以展示完整执行计划并等待确认。
14. 审批后计划变化会重新触发审批。
15. 发布成功后生成飞书文档、群消息和多维表格归档。
16. 重复回调不会重复发布。
17. Web 后台能展示完整节点轨迹、Tool 调用、审批和重试记录。
18. GitHub PAT 和其他密钥不出现在接口、日志、Trace 或 State 中。
19. 服务重启后，等待审批的运行仍可恢复。
20. 所有核心测试通过，Docker Compose 可以一键启动。

## 22. Codex 开发约束

Codex 实施时必须遵循：

1. 先阅读本文档并输出需求理解、风险和技术假设。
2. 在写业务代码前先生成：
   - 架构设计文档；
   - API 设计文档；
   - 数据库设计；
   - LangGraph 状态图；
   - 实施计划；
   - 测试计划。
3. 未经确认不得扩大 MVP 范围。
4. 每个 Task 必须有明确输入、输出和验收标准。
5. 每完成一个独立 Task 后运行相关测试。
6. 禁止把所有逻辑写入单个 Agent 节点或单个 Service。
7. 禁止在业务代码中硬编码飞书表字段、仓库或群 ID。
8. 禁止在 LangGraph State 中保存明文密钥和大规模原始数据。
9. 禁止让 LLM 直接负责数值计算、权限判断和幂等判断。
10. 所有外部写操作必须经过统一副作用执行器。
11. 所有 HITL 操作必须基于持久化 Checkpoint。
12. 所有外部平台调用必须有接口抽象和 Mock。
13. 实现完成前不得宣称功能可用，必须提供测试和验证证据。

## 25. 产品成功标准

该项目成功的判断不以“能生成一份周报”为标准，而以是否能够清晰展示以下能力为标准：

- Agent能理解目标并形成可执行计划；
- Agent能调用多个真实业务 Tool；
- Agent能处理不完整和失败的数据；
- Agent能在循环中观察、诊断、行动和验证；
- Agent知道什么时候必须请求人工介入；
- 人工审批后可以从持久化状态准确恢复；
- 所有外部副作用安全、可控、幂等和可审计；
- 最终结论有证据、时间范围和置信度；
- 开发者可以在后台完整观察整个执行过程。
